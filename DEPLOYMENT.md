# CFRS — Deployment guide (live HTTPS)

CFRS is a Django app that also serves the recommendation model, so it deploys as
a single web service (not a static site). This guide uses **Render** (free tier,
Django-friendly, HTTPS included). The same app runs on Railway, Fly.io or AWS ECS
with equivalent settings.

A live prediction request never trains the model — the models are built once in
the build step and loaded at startup.

## What's already set up
- `DEBUG`, `SECRET_KEY`, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS` read from env.
- WhiteNoise serves static files; `collectstatic` runs in the build.
- `DATABASE_URL` → Postgres in production; SQLite locally.
- Production security on when `DEBUG=False` (SSL redirect, secure cookies, HSTS).
- `build.sh` (install → generate dataset → train models → collectstatic →
  migrate → seed), `Procfile` (gunicorn), `render.yaml` (one-click blueprint).

## Deploy to Render
1. Push this project to a GitHub repo (see "Prepare the repo" below).
2. On https://render.com → **New → Blueprint** → connect the repo. Render reads
   `render.yaml` and creates the **web service + free Postgres**.
   (Or **New → Web Service** manually: Build `./build.sh`, Start
   `gunicorn config.wsgi:application`, and add a free Postgres, setting
   `DATABASE_URL` from it.)
3. Set the environment variables Render marks as "sync:false":
   - `DJANGO_ALLOWED_HOSTS` = `your-app.onrender.com` (add your domain later)
   - `DJANGO_CSRF_TRUSTED_ORIGINS` = `https://your-app.onrender.com`
   - `CFRS_ADMIN_PASSWORD` = a password you choose (stable admin login)
   - `DJANGO_SECRET_KEY` is auto-generated by Render (leave it).
4. Deploy. Watch the build log; it ends with the seed summary. Open the
   `.onrender.com` URL over HTTPS.

## Real email (so OTP reaches real users)
Console mode (no SMTP) only prints codes to the log — fine for your own testing,
not for real users. To send real emails, set in Render:
`EMAIL_HOST`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `DEFAULT_FROM_EMAIL`
(e.g. a Gmail App Password, or a transactional provider like Brevo/SendGrid).

## Google / GitHub login in production
In each provider, add the **production** callback URL alongside the local one:
- Google redirect URI: `https://your-app.onrender.com/accounts/google/login/callback/`
- GitHub callback URL: `https://your-app.onrender.com/accounts/github/login/callback/`
Then set `GOOGLE_CLIENT_ID/SECRET` and `GITHUB_CLIENT_ID/SECRET` in Render.
(Leave them blank to run with email/password only.)

## Prepare the repo
Exclude secrets and generated artefacts (already in `.gitignore`): `.env`,
`db.sqlite3`, `staticfiles/`, `*.pkl`, `ml/data/transactions.csv`. The FAO source
CSVs are tracked so the build can train. Commit `.env.example` (no secrets).

## Verify the live release (record this as evidence)
- Home, marketplace, login, register load over HTTPS.
- Register → a 6-digit code arrives (inbox if SMTP set, else build/console log) →
  verify → dashboard.
- `GET /logout/` returns 405 (logout is POST-only); the Sign-out button works.
- Buyer "Get recommendations" returns live matches tied to real active listings.
- Admin dashboard shows real DB figures; charts render.
- An unverified user cannot reach `/dashboard/` by typing the URL.

## Keep assessor access
Record the live URL, the repo + release tag, the admin login, and the model
version. Free Postgres and free web services can sleep or expire — note the dates
and keep the service available through the assessment window.
